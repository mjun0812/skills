# 図と画像の規則

## 表現の選択

| 内容                                   | 手段                                       |
| -------------------------------------- | ------------------------------------------ |
| 分岐のある処理                         | Mermaid `flowchart TD`                     |
| 複数の登場人物の往復                   | Mermaid `sequenceDiagram`                  |
| 状態遷移                               | Mermaid `stateDiagram-v2`                  |
| データ間の関係                         | Mermaid `erDiagram`                        |
| 配置が重要な構成・層構造・before/after | SVG                                        |
| UIの症状・実際の表示結果               | PNGスクリーンショット                      |
| 多数の測定値の傾向                     | 実測データから生成したSVGまたはPNGのグラフ |

- 作成前に、図で伝える関係や差異を1文で定める。短い文章で十分に理解できる場合は図を追加しない
- 1図1主題に絞る。直前に要点を書き、図の下に読み取り方や条件を説明する。結論や条件を図だけに閉じ込めない
- ラベルは本文で説明済みの語を使い、本文と同じ言語で短く書く。新しい用語は本文で先に説明する
- 実際の画面と提案用モックを区別し、モックにはその旨を明記する。実測値や実際の画面を推測で生成しない

## Mermaid

- 本文の `mermaid` コードブロックへ直接書く。通常の処理図は画像に変換しない
- GitHubで対応する構文を使い、独自の初期化設定・外部CSS・HTMLラベルに依存しない
- 縦方向を基本とし、長いラベルや交差を減らす。ノードが15個を超える場合は主題ごとに分ける
- ローカルの描画手段があれば構文と表示を確認する。ローカル描画の成功をGitHubでの描画確認と同一視しない

## SVG・PNG

- SVGは単体で表示できるファイルとして作り、背景・文字・線・必要なスタイルを内部で完結させる。親ページのCSS、class定義、継承色に依存しない
- 固定背景と十分なコントラストを使い、色で区別する場合はラベルや凡例も付ける
- ラベルに合わせた箱幅、図の外側の余白を取り、文字切れや矢印の重なりを避ける。本文に埋め込む大きさで読めることをローカル表示で確認する
- before/afterは比較条件を揃え、撮影対象や測定条件を本文に記す。元画像の意味を変える加工はしない
- 画像には説明的なalt textを付け、再現手順・コマンド・数値はコピーできる本文にも残す

## 添付と確認

1. 添付を使う場合だけ `gh --version` と対象のcreateコマンドの `--help` を確認する。gh v2.99.0以上の `--attach` を使う。画像のアップロードには対象リポジトリへの書き込み権限が必要で、GitHub Enterprise Serverはこの対応の対象外。条件を満たさない場合は添付付き投稿を停止して不足を報告し、旧版用アップロード処理は追加しない
2. 本文と添付をローカルで完成させてから投稿する。添付の実体、本文内の位置、alt textを確認する
3. 本文には `![Retry flow before and after the change](./retry-flow.svg)` のような参照を置き、createコマンドへ `--body-file <body.md> --attach ./retry-flow.svg` を渡す。同じ作業ディレクトリで実行し、本文とフラグのパスを一致させる。添付ごとに `--attach` を繰り返す。本文に参照が無い添付は末尾に追加されるため、配置を決める場合は必ず参照を書く
4. 投稿後は本文を再取得し、添付のローカルパスがアップロード先URLへ置換されたことと、Mermaidブロックが保持されたことを確認する。本文の再取得だけでは描画成功とは扱わない。描画を確認できなかった場合は、その範囲を結果に明記する
5. 投稿や確認に失敗した場合は本文と画像を残し、作成済みのURLと未完了の範囲を報告する。画像の再アップロード目的でIssue・PRを重複作成しない
