# github-issue-polish

[English](README.md)

既存のGitHub issueを、実装者が追加調査なしで着手できる状態まで磨き上げる。コードベース調査で原因と変更箇所を特定し、設計の分岐点を根拠付きで決定し、一時worktreeでのお試し実装で修正方針を検証した上で、承認を得て反映する。自分が作成したissueは本文を書き換え、他人が作成したissueは本文を変えずにコメントで提案する。

磨き上げ後の本文は、背景・目的、現状、`path:line`単位の原因分析、却下した代替案を含む修正方針、変更対象ファイル、テスト方針、やらないこと、検証メモ、意思決定ログ、完了条件で構成する。埋められないセクションは省略する。新規にissueを起票する場合は[`github-issue-create`](../github-issue-create/README_ja.md)、issueの実装からPR作成までは[`github-issue-resolve`](../github-issue-resolve/README_ja.md)を使う。

## 使い方

- 「issueを磨いて」
- 「#Nをpolishして」
- 「issueを実装できるレベルに詰めて」

```text
/github-issue-polish 123
/github-issue-polish 123 language=en --skip-trial
/github-issue-polish #123 --dry-run
```

## 引数

| 引数           | 効果                                                          |
| -------------- | ------------------------------------------------------------- |
| `issue`        | 対象のissue番号(必須)。先頭の`#`は省略可。                    |
| `language`     | 磨き上げ後の本文の言語。デフォルトは元issue本文の言語。       |
| `--skip-trial` | worktreeでのお試し実装を省略する。                            |
| `--dry-run`    | 磨いた本文の提示で停止する。issueへの書き込みは一切行わない。 |

## 動作

- issueが既にclosedの場合、または`gh`が未認証の場合は停止する。
- issue本文とコメントを目標の構成と比べてギャップを列挙する。コメントでの合意事項は本文へ反映する。
- コードを調査し、原因と変更箇所を`path:line`単位で特定する。issueのスコープ外の問題は、本文に混ぜず「やらないこと」への記載と別issue化の提案に回す。
- 設計の分岐はユーザーに質問せず自分で決める。決められない分岐は確信度を低くした暫定決定とし、意思決定ログ(論点 / 決定 / 根拠 / 確信度)で「要確認」と明示する。
- お試し実装: `polish/<issue-number>-trial`のworktreeを作成して最小実装とテストを行い、結果を検証メモに要約する(diff全文はissueに載せない)。worktreeとbranchは、エラーや中止の場合も含めて必ず削除する。
- 磨いた本文の全文、変更点サマリ、反映先を提示し、承認(反映する / 修正して再提示 / キャンセル)を取る。
- 反映先はissueの作成者で決まる。
  - 作成者が認証ユーザーなら、`gh issue edit --body-file`で本文を上書きし、変更点サマリをコメントとして1件投稿する。
  - 作成者が他人なら、本文とタイトルは書き換えず、磨いた本文と変更点サマリを提案として1件のコメントに投稿する。
- 最終報告として、変更したセクション、確信度が低く要確認の項目、別issue化を提案するスコープ外の問題を示す。
