<!--
記述ルール:
- 概要には PR の変更内容だけを1〜2文で書く。レビュー結果や指摘件数の要約は書かない
- CI に失敗がある場合と Contract 軸をスキップした場合は、概要にその旨を1行ずつ追加する
- 指摘事項には verifier が confirmed と判定した Finder と Standards と Contract SubAgent 由来の指摘のみを書く
- Standards / Contract SubAgent 由来の指摘もmergeをブロックしVerdictに影響する
- 指摘事項がない場合は見出しを残し中身を「なし」と書く
- 指摘は `### N. [カテゴリ] 要約` の見出しで1件ずつ区切り、Finder由来、Standards由来、Contract由来の順に並べて全体を1から連番にする
- カテゴリは問題の主な実害または種類を表す短いラベルにする
- 要約は実害だけを1文で書き、原因は `問題` に書く
- 項目名は太字にして1行に置き、内容は次の行から書く。項目の間は空行で区切る
- Finder由来の各項目には `場所` / `問題` / `発生経路` / `完了条件` を含める
- Standards由来とContract由来の各項目には `場所` / `問題` / `根拠` / `完了条件` を含める
- `他の該当箇所` と `補足` は該当があるときだけ `完了条件` の前に置く
- Finder由来の `問題` には発生条件・原因・具体的な実害だけを3文以内の1段落で書く
- Standards由来の `問題` にはdiffで観察できる事実と、merge後への先送りが安全でない理由をまとめる
- Contract由来の `問題` には実装の現状と、contractの約束との食い違いをまとめる
- `発生経路` は番号付きリストにし、問題へ到達する実行パスを1ホップ1行の `file:line` (説明) で書く
- `根拠` は箇条書きにし、Contract由来ではspecの該当記述の引用と実装の `file:line` を書く
- `他の該当箇所` には同じ問題を持つ他の `file:line` を1行1箇所の箇条書きで書く
- `補足` には変更前や踏襲元との比較など、核心ではないが判断に役立つ事実を箇条書きで書く
- `完了条件` は箇条書きにし、実装方法ではなく、問題が解消されたと判断できる状態を1条件1文で書く。補足が必要な場合だけ次の行に1文添える
- Finder と verifier の生の `証拠` と検証ログはレビュー本文と inline comment に書かない。到達経路は `発生経路` として校正した形で書く
- 最終レビューに指摘事項以外の指摘セクションは作成しない
- inline comment 化されるのは指摘事項セクションのみ
