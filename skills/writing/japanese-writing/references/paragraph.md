# パラグラフライティング

書き手の主張と根拠を読み取らせる文書を、段落の先頭だけを拾って読める形に書く規範。
すべての文章には適用しない。最初に、適用する文書かどうかを決める。

## 適用する文書

読者が、書き手の主張とその根拠を読み取るための散文に適用する。

| 適用する                       | 適用しない                                             |
| ------------------------------ | ------------------------------------------------------ |
| 設計文書、調査報告、調査メモ   | 体験記、エッセイ、小説、紹介記事、脚本                 |
| 提案書                         | メール、チャット                                       |
| 障害報告の原因と対策を述べる節 | 障害報告の時系列の経過                                 |
| READMEの説明の節               | 手順書の手順、リファレンスの項目                       |
| 技術記事、論文                 | 議事録、スライド、PR説明の箇条書き、規程や仕様書の条文 |
|                                | 場面や例で読ませる書籍の章                             |

- 1つの文書に両方が入っているときは、節ごとに決める。
- 箇条書き、番号付きリスト、表の中には適用しない。
- 場面や例で読ませる書籍の章は、[argument.md](argument.md) の構成に従う。
- 起きたことを時間の順に述べる技術記事は、「経緯を順に語る記事」に従う。
- 依頼で「パラグラフライティングで」と指定されたときは、上の表で適用しないとした文書にも適用する。

## 段落の形

1つの段落は、1つの主題文と、それを支える支持文でできている。

- **主題文**：段落の先頭に置く文。その段落で言いたいこと(判断、結論、評価、事実の要点)を1文で述べる。
- **支持文**：主題文に続く文。根拠、データ、具体例、条件、理由を述べる。

主題文は主張を述べる。話題を示すだけの文や、作業を報告するだけの文は主題文にならない。

| 主題文にならない文                                             | 主題文                                                             |
| -------------------------------------------------------------- | ------------------------------------------------------------------ |
| CIが遅い原因を調べた。                                         | CIが遅い原因は、依存の取得でキャッシュが使われていないことである。 |
| 固定間隔の再送について述べる。                                 | 固定間隔の再送は、障害時にリクエストを集中させる。                 |
| サーキットブレーカーは、失敗が続いたら再送を止める方式である。 | サーキットブレーカーは採用しない。今回の原因には過剰である。       |

- 1つの段落には1つの主題だけを置く。主題文を1文で書けない段落は、主題が2つ以上ある。段落を分ける。
- 支持文には、主題文を支える内容だけを書く。支えない文は、別の段落へ移すか削る。
- 主題文には、数値や固有名を入れてよい。
- 段落の最後で、主題文を言い直さない。
- 主題文だけの段落は、支持がない。支持になる内容が文書の中にあればそこへ集め、なければ前後の段落に入れる。支持を作って足さない。
- 段落の中の文が8つを超えたら、主題が2つないかを確かめる。

## 段落のつなぎ

- 主題文だけを上から拾って読むと、文書の要旨が分かるように書く。
- 段落は、論理の順(原因から結果、全体から部分)か、重要な順に並べる。
- 主題文の頭で、前の段落との関係を接続表現か既出の語で示す。

## 文書の構成

文書は、総論、各論の順に書く。

- **総論**：文書の最初の段落。文書の結論と、その主な根拠を述べる。報告や提案では、読み手に求める判断や作業と、その期限も述べる。
- **各論**：総論で挙げたことを、挙げた順に述べる。

総論は内容を述べる。これから何を書くかの予告は総論にならない。

| 予告                              | 総論                                                                                                           |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 本文書では、再送方式を3つ比べる。 | 再送には、指数バックオフにジッターを加えた方式を採用する。障害時にリクエストが集中することを防げるためである。 |
| 以下に調査の結果をまとめる。      | CIの所要時間は、キャッシュのキーを直すと18分から約12分になる。修正は今週入れる。                               |

- 節も同じ形にする。節の最初の段落で、その節の結論を述べる。
- 対象読者、前提、動作を確認した環境を示す案内は、総論の直後に置く。
- 見出しは節が扱う対象を示し、主題文がその対象についての主張を述べる。見出しに主張を書かない。
- 総論を言い直すだけの結びの節は置かない。結びに書くのは、今後の予定、未決の事項、次の作業である。
- 適用する文書では、新しい概念を定義の文から始めてよい。結論を、反論の処理より前に置いてよい。

## 経緯を順に語る記事

起きたことを時間の順に述べる技術記事(不具合の調査の記録、検証の記録、移行の記録)は、冒頭の総論だけを適用する。

- 冒頭に総論を置く。分かった原因や結果と、行った対処を述べる。分かっていないことが残っていれば、それも述べる。
- 節の順序は、時間の順のまま保つ。
- 経緯を語る段落では、文の順序を時間の順のまま保つ。結果の文を段落の先頭へ移さない。
- 仕組みや理由を説明する段落にだけ、主題文を先頭に置く規則を適用する。

経緯を語る段落かどうかは、文が「〜した。次に〜した。すると〜だった」のように、行ったことと分かったことを順に述べているかで決める。

## 修正での扱い

適用する文書を直すときは、段落の中だけでなく、文書全体を組み替える。

1. 段落ごとに、その段落の主張を1文で書き出す。
2. 主張を1文で書けない段落を直す。主題が2つ以上あれば段落を分ける。主張がなく支持だけなら、支える先の段落へ入れる。
3. 各段落で、主張の文を先頭へ移す。主張が文になっていなければ、段落の中身から主題文を書く。
4. 文書の結論を見つけ、最初の段落に総論を置く。結論が後ろの節にあれば、前へ移す。
5. 段落と節を、総論で挙げた順か、重要な順に並べ替える。
6. 総論へ移して中身がなくなった結びの節は、見出しごと削る。
7. 修正後の主題文だけを上から読み、文書の要旨になっていることを確かめる。

- 主題文と総論は、原文にある内容だけで組み立てる。原文にない主張、評価、数値を足さない。
- 組み替えても情報を落とさない。数値、条件、例外、未確認の事項は、どこかの支持文に残す。
- 「変更点」には、移した段落、分けた段落、まとめた段落を挙げる。足した総論と主題文も挙げる。足した総論と主題文には、もとにした原文の箇所を添える。
- 原文の主張どうしが食い違うときは、どちらかに決めず「要確認」に挙げる。
- テンプレート、論文の章立て、依頼で指定された見出しのように、構成が決まっている文書では、見出しの数と順を保つ。組み替えるのは節の中だけにする。
- 依頼で構成を変えないよう指定されたときは、段落の中だけを直す。
