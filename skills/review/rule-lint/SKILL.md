# rule-lint

## 概要

文章の規約は読まれずに破られる。
チェックにすれば、人間もagentも編集のたびに違反を知る。
このSkillでは、規約をチェックへ変換し、チェックが正しく働くことを確かめ、開発のloopへ接続するまでを1単位とする。

## 手順

1. 規約を集める。
   出典の指定がなければ、`CLAUDE.md`、`AGENTS.md`、`.mjun/steering/`、ADR、READMEの規約節を読む。
   レビュー指摘から集める場合は、2回以上出た指摘だけを対象にする。
2. 規約ごとに判定する。
   - 完全: 規約の文面が対象とする書き方を、チェックがすべて判定できる。
   - 部分: 一部の書き方しか判定できない。名前による近似や、複雑度などの代理指標がこれにあたる。
   - 不可: 手順・判断・プロセスに関する規約。
3. チェック手段は、次の順で最初に使えるものを選ぶ。
   1. 既存linterのルールの有効化と設定
   2. ast-grepルール
   3. script
4. チェックを作り、「チェックごとに満たす条件」をすべて満たす。
5. 既存コードに違反が1件以上あれば、次の選択肢をユーザーに示して選んでもらう。
   - 既存の違反を直す。
   - 既存の違反をbaselineとして記録し、新しい違反だけを落とす。
   - 警告として導入し、違反がなくなったらerrorへ上げる。
6. 規約文書を判定に合わせて更新する。
   - 完全: 文章を削除し、チェックの場所を書く。
   - 部分: 文章を残し、チェックが拾う範囲と拾わない範囲を書き添える。
   - 不可: 文章のまま残す。

   チェックを成り立たせるために新しい規約(命名の制約など)が必要になったら、文書へは書かずにユーザーへ提案する。

7. 「報告」の形式で報告する。

## チェックごとに満たす条件

- メッセージ: 何が違反かと、どう直すか(使うAPIや書き方)を書く。
  例: `` `np.random.seed` を直接呼ばず `trainer.utils.set_seed()` を使う ``
  既存linterのルールでメッセージを変えられない場合は、そのルールを使い続け、直し方は規約文書のチェックの場所に添える。
- テスト:
  - ast-grep: 検出する例と検出しない例を書き、`ast-grep test` を通す。
  - script: 違反例と正例のfixtureを入力にしたテストを書き、リポジトリのテストrunnerで実行する。
  - linter設定(`banned-api`、`per-file-ignores` など): 違反を含む一時ファイルに実行して検出を確かめ、確認後に消す。
- 例外: 正当な例外は、設定ファイルのファイル単位の除外に理由のコメントを付けて書く。
  inlineの抑制コメント(`# noqa`、`// eslint-disable`、`ast-grep-ignore`)は使わない。
  抑制コメントをチェックするルールがあれば有効にする(ruffの `PGH004`・`RUF100`、eslintの `--report-unused-disable-directives` など)。
- 接続: ローカルのgit hook(pre-commit、prek、lefthookなど)とCIの両方で実行する。
  agentのhook(Claude Codeの `.claude/settings.json` など)がリポジトリにあれば、そこにも追加する。

## 報告

対象にしたすべての規約を、次の表で報告する。

| 規約 | 判定 | チェック | テスト | 接続先 |
| ---- | ---- | -------- | ------ | ------ |

表に続けて、次を書く。

- 既存の違反の件数と、選ばれた導入方針
- 「部分」の規約が拾わない範囲
- 「不可」の規約と、その理由
- ユーザーへ提案する新しい規約(あれば)
